    What's new in 0.19.0

    The first stable release since 0.17.1. It contains everything in the release candidates 0.17.2-rc.1 to 0.19.0-rc.4 (each in the changelog), plus the fixes in this section. The main changes since 0.17.1:

    • generate, check and plan no longer wait for Maven or Gradle after an entity edit.
    • PostgreSQL: a migration waits at most 5 seconds for a table that another session has locked (MXE117, --table-lock-timeout), so queries on that table don't queue behind it.
    • generate asks whether to keep the data it drops, so a rollback can restore it; rollback warns about data its scripts can't bring back.
    • verify starts its throwaway database in the version of yours.
    • New lint rule MX018 (transaction control in a migration); import lists what still ties the project to the old tool; JSON output for status, generate, plan and check.
    • Security: passwords stay hidden in more URLs and messages, the MCP server only reads files of the project, and the container image has the fixed Java (CVE-2026-114938), apt (CVE-2026-109518) and newer JDBC drivers.

    Security¶

    • Migrax refuses table, column and constraint names with a line break or another control character (MXE118), whether they come from the entities, the schema file, the database (the first generate) or .migrax/snapshot.json. A line break in a name ended a comment line in the rollback script, and the rest of the name ran as SQL on rollback. Messages, errors, plan/check/diff reports, lint findings and drift show such characters as text (an escape character as \u001b) instead of sending them to the terminal.
    • MySQL, MariaDB and TiDB: a backslash in a table or column comment, a table-generator sequence name or a text default of a schema file (read back through a MySQL or TiDB database) is now written as \\. These databases read \' as a quote inside the string, so a comment such as x\'; DROP TABLE t; -- ended the string early and the rest ran as SQL, and a comment ending in \ (C:\temp\) broke the migration.
    • On PostgreSQL, a migration with a COMMIT hidden behind an E'...' string ending in \', or after a name ending in $$ (including a name with non-ASCII letters), was reported as MXE117 "Nothing was changed" when it then waited too long for a table lock, although the statements before the COMMIT were committed. It is now recorded as failed.
    • import no longer shows values written in Groovy slashy strings (/.../, $/.../$) or triple-quoted strings, and shows a quoted group:artifact only where it is a dependency; elsewhere it says flyway coordinate or liquibase coordinate.

    What's new in 0.20.0-rc.3

    Release candidate for 0.20.0, for testing.

    Added¶

    • Tested on Supabase Postgres 17, AlloyDB Omni 17 and Vitess 24 (the engine behind PlanetScale), with the same checks as every other database. On Vitess, generate --zero-downtime can't be used: Vitess doesn't accept the triggers Migrax writes.
    • Tested on PostgreSQL 17 with TimescaleDB, PostGIS or pgvector installed, and on Percona Server for MySQL 8.4.

    Fixed¶

    • Check constraints read from an existing database or a schema file are listed in name order, so the SQL Migrax writes for them is the same on every run.
    • PostgreSQL: tables, views and sequences that belong to an extension are left alone. Before, clean stopped with "cannot drop view ... because extension pg_stat_statements requires it", and the first generate on a PostGIS database offered to drop spatial_ref_sys.
    • Hibernate 8 projects (tested with 8.0.0.CR1) are now read through Hibernate's own mapping. Before, Migrax warned that it could not read the mapping and fell back to scanning annotations, which can give a different schema (in our test, a sequence was missing).

    Container image¶

    From Migrax 0.3.0 on, every release is also a container image with the common JDBC drivers, for running migrations in Kubernetes or CI without a Java project:

    docker pull ghcr.io/fsmutimeer/migrax:0.19.0

    See Containers and Kubernetes.

    Check your download¶

    Each file's SHA-256 checksum is listed above and in SHA256SUMS. To check a file:

    certutil -hashfile migrax-0.19.0.zip SHA256

    shasum -a 256 migrax-0.19.0.zip

    sha256sum migrax-0.19.0.zip

    The result must match the checksum on this page.

    From Migrax 0.17.1 on, you can also check that a file was built by Migrax's own release workflow on GitHub, from this repository's code, with the GitHub CLI:

    gh attestation verify migrax-0.19.0.zip -R fsmutimeer/migrax

    Each release also lists every library its files contain in migrax-<version>-sbom.cdx.json (CycloneDX format), for security scanners and license checks. The container image keeps its own software list and build record in the registry:

    docker buildx imagetools inspect ghcr.io/fsmutimeer/migrax:0.19.0 --format '{{ json .SBOM }}'
docker buildx imagetools inspect ghcr.io/fsmutimeer/migrax:0.19.0 --format '{{ json .Provenance }}'

    Which file do I need?¶

    • To use the migrax command: the .zip. It contains the command line tool and its installers.
    • The .jar files are libraries for build tools and frameworks: the core library with the Maven plugin, the Gradle plugin, and the startup integrations for Spring Boot, Quarkus, Micronaut and Helidon. Maven and Gradle normally download these themselves; see Frameworks.
