    What's new in 0.17.1

    Added¶

    • Every GitHub release lists the libraries it contains in migrax-<version>-sbom.cdx.json (CycloneDX), and each of its files has a signed record of the workflow run that built it: gh attestation verify <file> -R fsmutimeer/migrax checks it. The container image carries its own software list and build record in the registry. See Download > Check your download.

    Fixed¶

    • Renaming a table no longer needs --allow-destructive. Hibernate's foreign key names contain the table name, so generate --rename-table (or answering "yes" to "Did you rename table ...?") dropped the old key and added it again under its new name, and the drop was counted as a destructive change. A foreign key that comes back unchanged under a new name in the same migration is no longer destructive; one that is really removed or changed still is. It is listed as "rename foreign key ..." ("kind": "rename_foreign_key" in plan --json and diff --json). On PostgreSQL, CockroachDB, YugabyteDB and H2 the migration renames the key (RENAME CONSTRAINT); other databases drop it and add it again, which checks every row.
    • SQLite: the rollback of a table rename lost the other changes to that table (a renamed foreign key, a changed column). SQLite makes them by rebuilding the table, and the rollback looked the table up under the name it gives back only afterwards, so the rebuild was left out without a word. It is now rebuilt under that name, and a table that can't be found stops migrax generate with an error instead.
    • Oracle: making a NUMBER column smaller (fewer decimals or fewer digits before the point, bigint to integer included) failed with ORA-01440 once the table had rows, in a migration or in the rollback of one that made it larger. Oracle allows that only on an empty column, so the change now goes through a new column: first a check that every value fits unchanged (a value with too many digits or decimals stops the migration with a message saying how many, before the column is changed, and so does an index, constraint or column grant made by hand that dropping the column would remove), then the new column is added, a trigger keeps it up to date while the application goes on writing, the values are copied and checked once more, the old column is dropped (writes fail for a moment there) and the new one gets its name, default, NOT NULL and comment. The table is rewritten and the column moves to its end; the migration account needs CREATE TRIGGER. Columns in a key, index, unique constraint or check, and identity columns, keep the plain change, which Oracle still refuses once they have values (see Reference > Limitations).

    Security¶

    • Container image: newer JDBC drivers without known vulnerabilities. PostgreSQL 42.7.5 to 42.7.14 (could fall back to weaker authentication despite channelBinding=require, and a server could make it spend CPU on SCRAM), MariaDB 3.5.1 to 3.5.11 (could send the password in clear text to a server in the middle), SQL Server 12.8.1 to 13.6.1 (did not check some input from the server well enough). URLs with encrypt and trustServerCertificate work as before (tested on SQL Server 2022). The CLI download bundles no drivers and is not affected.
    • Container image: the base images are pinned to exact versions, so every build of a release ships the same thing, and /usr/bin/pebble, a program of the base image that Migrax never runs and that scanners report, is removed.
    • The published POMs no longer name library versions with known vulnerabilities (Micrometer, OpenTelemetry, Spring Boot). Migrax never bundled them: your application keeps its own versions, and the framework versions Migrax works with are unchanged.
    • The GitHub Action (uses: fsmutimeer/migrax@...) runs the actions it uses at exact commits instead of version tags, so a moved or compromised tag can't change what runs in your workflow.

    What's new in 0.18.0-rc.1

    First release candidate for 0.18.0, for testing: it includes everything in 0.17.2-rc.3, adds the entity class to the JSON of plan and check, and makes generate ask about the most likely rename first. It is not on Maven Central: use the CLI from the Download page or the container image ghcr.io/fsmutimeer/migrax:0.18.0-rc.1.

    Added¶

    • plan --json and check --json name the entity class and the column of each change (entity, column), so an editor can point at the class that needs a migration. check --json also lists each change as an object in operations; changes stays as it was. entity is filled when the entities are read with Hibernate 5 or newer or by annotation scanning, and is null for the other readers for now, and for join, collection and secondary tables.

    Fixed¶

    • When a column disappears and several new columns of the same type appear, generate now asks about the most similar one first (name -> full_name before name -> country) and, after a "no", asks about the next one. Before, it asked only about the first new column in the table, and the "Possible rename" hint printed without a terminal pointed at that one too. At most three questions are asked per column, and Migrax stops asking when the input ends (Ctrl-D).
    • The container image is built on a newer eclipse-temurin:21-jre, which fixes CVE-2026-111497 in the operating system's Brotli library (libbrotli1).

    Container image¶

    From Migrax 0.3.0 on, every release is also a container image with the common JDBC drivers, for running migrations in Kubernetes or CI without a Java project:

    docker pull ghcr.io/fsmutimeer/migrax:0.17.1

    See Containers and Kubernetes.

    Check your download¶

    Each file's SHA-256 checksum is listed above and in SHA256SUMS. To check a file:

    certutil -hashfile migrax-0.17.1.zip SHA256

    shasum -a 256 migrax-0.17.1.zip

    sha256sum migrax-0.17.1.zip

    The result must match the checksum on this page.

    From Migrax 0.17.1 on, you can also check that a file was built by Migrax's own release workflow on GitHub, from this repository's code, with the GitHub CLI:

    gh attestation verify migrax-0.17.1.zip -R fsmutimeer/migrax

    Each release also lists every library its files contain in migrax-<version>-sbom.cdx.json (CycloneDX format), for security scanners and license checks. The container image keeps its own software list and build record in the registry:

    docker buildx imagetools inspect ghcr.io/fsmutimeer/migrax:0.17.1 --format '{{ json .SBOM }}'
docker buildx imagetools inspect ghcr.io/fsmutimeer/migrax:0.17.1 --format '{{ json .Provenance }}'

    Which file do I need?¶

    • To use the migrax command: the .zip. It contains the command line tool and its installers.
    • The .jar files are libraries for build tools and frameworks: the core library with the Maven plugin, the Gradle plugin, and the startup integrations for Spring Boot, Quarkus, Micronaut and Helidon. Maven and Gradle normally download these themselves; see Frameworks.
