    Your entities change.
    Migrax writes the migration.

    Database migrations generated from your JPA entities: plain SQL with a rollback script, linted for locking and data loss, and verified against your own Hibernate, EclipseLink or OpenJPA mapping before it reaches production.

    See it in 30 seconds

    Change an entity, and Migrax writes the SQL and the script that undoes it.

    Customer.java
       @Column(nullable = false, length = 100)
   String name;
+
+  @Column(length = 30)
+  String phone;
 }
    0002_add_customers_phone.sql
    ALTER TABLE customers ADD COLUMN phone varchar(30);
    rollback/0002_add_customers_phone.sql
    -- Note: deletes data written to customers.phone since the migration ran.
ALTER TABLE customers DROP COLUMN phone;

    The new column, and a rollback script that says which data undoing it would delete.

    Customer.java
    -  @Column(nullable = false, length = 100)
-  String name;
+  @Column(name = "full_name", nullable = false, length = 100)
+  String fullName;
    0003_rename_customers_name.sql
    ALTER TABLE customers RENAME COLUMN name TO full_name;
    rollback/0003_rename_customers_name.sql
    ALTER TABLE customers RENAME COLUMN full_name TO name;

    A dropped column next to a new one looks like a rename. Migrax asks, and renames it so the data stays; in CI it stops and tells you to pass --rename.

    PurchaseOrder.java
    @Entity
@Table(name = "orders")
public class PurchaseOrder {
  @Id
  @GeneratedValue(strategy = GenerationType.IDENTITY)
  Long id;

  @ManyToOne(optional = false)
  Customer customer;

  @Column(nullable = false, precision = 12, scale = 2)
  BigDecimal total;
}
    0004_create_orders.sql
    CREATE TABLE orders (customer_id bigint NOT NULL, id bigint GENERATED BY DEFAULT AS IDENTITY NOT NULL, total numeric(12,2) NOT NULL, CONSTRAINT orders_pkey PRIMARY KEY (id));
ALTER TABLE orders ADD CONSTRAINT fk_orders_customer_id_54d4cc52 FOREIGN KEY (customer_id) REFERENCES customers (id);
    rollback/0004_create_orders.sql
    -- Note: deletes data written to orders since the migration ran.
ALTER TABLE orders DROP CONSTRAINT fk_orders_customer_id_54d4cc52;
DROP TABLE orders;

    Nothing is dropped until you say --allow-destructive, and the rollback script warns that it can't bring the data back.

    Why teams use Migrax

    Everything a migration needs, checked before it reaches production.

    • Migrations written for you

      Change an entity, run migrax generate. Tables, columns, keys, indexes, join tables, element collections, sequences and inheritance come out exactly as your Hibernate, EclipseLink or OpenJPA maps them.

    • Checked before production

      Every migration is linted for statements that lock big tables, fail on existing rows or break running instances. migrax verify checks the result against your mapping, and Hibernate validates it itself.

    • Rollback included

      Each generated migration comes with a rollback script, and verify tests every one of them: roll back, apply again, same schema.

    • Asks before it loses data

      A dropped column that looks renamed? Migrax asks, and renames it so the data stays. Drops only happen when you say --allow-destructive.

    • Catches manual changes

      migrax drift compares the live database with what your migrations produce and lists every difference, including columns someone made narrower.

    • Zero setup

      Run it in your service folder. It compiles the project, finds the dependencies and reads the database settings from your application configuration.
